Redis além do cache: 5 usos que a maioria dos devs ignora

A maioria das pessoas usa Redis como cache e para por aí. Mas Redis é um banco de dados em memória extremamente versátil. Subutilizá-lo é deixar performance e simplicidade na mesa.

31 Mai 2026 · Luana Saraiva

Se você usa Redis no seu projeto, há uma boa chance de estar usando apenas uma fração do que ele pode oferecer. Cache de queries, cache de fragmentos de view: válido, mas longe do limite. Aqui estão cinco usos que vão além disso.

1. Distributed Lock

Quando múltiplos processos ou workers competem pelo mesmo recurso, você precisa garantir que só um execute por vez. Sem isso, você acaba com race conditions silenciosas que aparecem só em produção, nos piores momentos.

Redis resolve isso com SETNX (SET if Not eXists): você tenta setar uma chave. Se ela já existe, outro processo está executando e você aguarda ou descarta. Simples, eficiente e sem precisar de uma fila inteira pra isso. 

lock_key = "job:importacao:lock"
acquired = redis.set(lock_key, 1, nx: true, ex: 30)

if acquired
  # executa o job com segurança
ensure
  redis.del(lock_key)
end

2. Rate Limiting

Quer limitar quantas requisições um usuário pode fazer por minuto? Com INCR + EXPIRE você implementa um contador com TTL em poucas linhas, sem banco relacional, sem overhead. 

key = "rate_limit:#{user_id}:#{Time.now.to_i / 60}"
count = redis.incr(key)
redis.expire(key, 60) if count == 1

raise TooManyRequestsError if count > 100

A expiração automática do Redis garante que o contador seja zerado sem nenhuma tarefa de limpeza no seu lado.

3. Filas leves com Pub/Sub

Para eventos simples onde você não precisa de persistência garantida, o Pub/Sub do Redis é uma alternativa elegante a soluções mais pesadas como RabbitMQ ou Kafka.

Um serviço publica, outros assinam. Sem broker externo, sem configuração complexa. Ideal para notificações internas, invalidação de cache distribuído ou comunicação entre serviços leves. 

# publisher
redis.publish("pedidos:criados", pedido.to_json)

# subscriber (em outro processo)
redis.subscribe("pedidos:criados") do |on|
  on.message { |_channel, msg| processar(msg) }
end

4. Leaderboards em tempo real

Sorted Sets são uma das estruturas mais elegantes do Redis. Com ZADD e ZRANGE você tem inserção, atualização e leitura ordenada, tudo com complexidade O(log n). 

# adiciona ou atualiza pontuação
redis.zadd("ranking:semanal", pontos, user_id)

# top 10
redis.zrevrange("ranking:semanal", 0, 9, with_scores: true)

Implementar isso num banco relacional exigiria índices cuidadosos e queries de ordenação custosas. No Redis, é nativo.

5. Gerenciamento de sessões

Armazenar sessões de usuário no Redis é uma das práticas mais comuns em aplicações distribuídas e faz todo sentido. TTL nativo significa que sessões expiram automaticamente. Velocidade de leitura em memória significa autenticação sem latência.

Em Rails, basta configurar a session store: 

# config/initializers/session_store.rb
Rails.application.config.session_store :redis_store,
  servers: ENV["REDIS_URL"],
  expire_after: 2.hours

Conclusão

Redis não é só "o negócio que deixa a aplicação mais rápida". É uma ferramenta com estruturas de dados ricas: strings, lists, sets, sorted sets, hashes, streams. Cada uma com casos de uso específicos e bem definidos.

Vale a pena ler a documentação com atenção. Você vai descobrir que vários problemas que você resolve com workarounds complicados já têm solução nativa no Redis.
